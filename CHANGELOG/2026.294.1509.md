# 2026.294.1509 — fix(skills)!: the seven skill bodies move to the repo root, the one canonical base

## Summary

The seven skill bodies move from `candy/<candy>/.agents/skills/<name>/SKILL.md` to
`.agents/skills/<name>/SKILL.md` at this repo's root — the one canonical base — and the candy-dir
tree is deleted in the same commit. `AGENTS.md` carries the rule in the same commit, because it
stated the superseded candy-dir base twice.

**This reverses the layout consequence of a landed ruling, on direct operator instruction.** The
operator's words:

> *"Please fucking restore .agents/skills/ for all repos! That's the fucking purpose of this whole
> migration !!! And move any distro layer into separate repos like all other layers to and fix
> things properly following AGENTS.md and implement the same approach and architecture everywhere
> !!!"*

opencharly/sdk#434's ruling was right about the SHAPE — an image candy may not own a skill, and
`arch-skills` still owns all seven nodes — and wrong about the BASE its re-home chose. The root tree
is canonical; nothing is preserved beside it "for compatibility". The reader base is unified in
opencharly/sdk (`candyRepoRoot` in `deploykit`) so both readers resolve the root.

**Why the move is the fix, not a tidy-up.** Two readers, two bases, one layout:

| reader | resolves |
|---|---|
| `plugin-marketplace` (`skillfile.go`) | `<entity SourceRoot>/<tree>/<name>/SKILL.md` — the ref root, i.e. this repo's root for a whole-repo ref |
| `deploykit.CollectSkillBodies` (the label and `charly box validate`) | `<owner candy SourceDir>/<tree>/<name>/SKILL.md` — the candy dir |

At this repo's newest tag (`v2026.294.0225`) the corpus reader could reach **none** of the seven
bodies, and `charly marketplace generate` is fail-closed over the whole corpus, so no marketplace
refresh could be generated at all (opencharly/marketplace#522: 48 bodies over 10 refs; this repo is
7 of them).

## How tested

**The bodies MOVED rather than changed.** Byte-identity is proven by git OBJECT IDENTITY — each
file's blob SHA is the same object before and after the move — which does not depend on rename
detection:

The diff carries **771 insertions and 768 deletions across 15 files**. That number counts the same
bytes twice — once as a deletion at the old path and once as an insertion at the new one — because
this worktree has `diff.renames=false`, and it is off deliberately: the body has to name the old
path to show what moved, and the pre-push gate reads the old paths only when rename detection is
disabled. With git's default rename detection the same commit is **8 files: seven 0/0 renames plus
AGENTS.md 12/9**, which is why the blob SHAs above are the real evidence and the line count is not.
