## Summary

Re-nest the two `local:` members of `check-arch-vm` — `charly-cachyos-tailscale-test` and
`arch-host` — INSIDE the bed's `vm:` body, so each deploys into the disposable Arch guest instead
of onto the machine running charly; and make the bed's own gate run to completion, which the
re-nest needed in order to be provable at all.

This is the per-member determination `opencharly/charly#763` asks for (its `distro-arch` leg),
read from each member's own description and plan rather than assumed, plus the position fix. It
is this repo's leg of `opencharly/sdk#330`'s org-wide sweep.

Head `610f59a20f4c83e2897ba3dc6896000e752bf64d`.

**Successor to #52 — both halves of what closed it are answered here.** `opencharly/distro-arch#52`
was auto-closed after five BLOCK verdicts. Rounds 1 to 4 raised ONE blocking finding, the same each
time: A2/R10 — the required bed run was absent — while judging the placement, the mechanism and the
security screen correct. Round 5 raised that same absence for its new head AND the body drift it
had caused: the branch had grown a candy-pin bump and the ledger-check rewrites, and the body still

**The determination — IN-GUEST for both.**

- `arch-host` — its plan asserts the GUEST's install ledger. On the operator's workstation
  `/home/arch` does not exist, so the alongside position made those steps fail AS a host deploy —
  the opposite of what the member exists to prove. `opencharly/charly#748` records its stated
  intent as "host profile applied inside the guest".
- `charly-cachyos-tailscale-test` — the bed's own description calls it one of the "two nested
  local-target beds" the VM bed drives ("tailscale runtime wiring"); its plan asserts guest system
  state (`systemctl is-active tailscaled`, `systemctl is-enabled tailscaled.service`) that a host
  without those units cannot satisfy.

**The defect.** Both keys were authored at the SAME column as the bed's `vm:` kind key, so the
fold stamped them DEPLOY-LEVEL; every deploy-time consumer follows only `InSubstrateMembers()`, so
each was walked as its OWN root and landed on the machine running charly — the exact behaviour
`30cabf27` (#79) moved these beds into VMs to prevent. Re-indented into the `vm:` body (the
position `opencharly/charly#762` made loadable), each now deploys into the guest via the nested
local-member path, `spec/deploy.DeployNestedLocalChildren`.

**Running the gate surfaced three further defects on the same surface.** Each is measured below,
each is fixed here, and each would have left the bed red or unable to start:

1. **The bed could not deploy at all** (`opencharly/distro-arch#70`, blocker 1). A `vm:` deploy
   compiles no primary image plan, so its deploy plugin has to be in the project's candy closure;
   this closure carried none, and `[deploy-add]` died in 11.6 s with "the `vm` deploy substrate is
   not available in this project". The substrate now rides on the bed's own `add_candy` — the same
   host-side-plugin channel `plugin-spice` already uses in that list. Resolution is PROJECT-scoped
   (`plugin-fleet/candy/plugin-fleet/dispatch.go`, `targetOnlyRoute` over the project's
   external-target set), so this one composition serves every `vm:` deploy in the repo, not only
   this bed.
2. **The members' ledger checks asserted a DELETED tree.** `arch-host` asserted
   `~/.config/opencharly/installed/{deploys,layers}`; that per-deploy JSON tree is gone
   (`sdk/kit/install_ledger.go`: "There is no per-deploy JSON-file layout under
   ~/.config/opencharly/installed/"), and the ledger is now the `ledger:` section of the venue's
   per-host charly.yml, written on the SUBSTRATE's filesystem for a nested deploy
   (`AddCandyDeploymentVia` / `WriteDeployRecordVia`, whose own comment names this case). The three
   assertions are re-pointed 1:1 at the live shape, on the same three check ids.
3. **The direnv candy red-blocked the venue it is deployed into.** `layer-direnv`
   v2026.272.0057's three image-shaped build-artifact checks are UNSCOPED, so the per-child
   `check live` runs them in THIS deploy venue, which bakes no `/etc/profile.d` drop-in
   (`opencharly/layer-direnv#7`, filed from this bed). `v2026.287.2155` scopes them to
   `context: [build]` and adds the deploy-venue assertion; the pin takes that tag.
