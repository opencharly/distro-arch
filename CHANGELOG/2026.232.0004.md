# 2026.232.0004 — document the auto-merge landing flow in the README

The README gains a "Landing & releases" section that describes the only way a
change reaches `main` in this repo: a fresh `charly/pr-validator` AI review
must pass on the PR head, the auto-merge engine waits until every status check
is green, finalizes the placeholder CHANGELOG to the merge-time CalVer (rename
+ H1 rewrite + the `auto-merge-finalized` marker-comment), re-runs the
validator on the finalized head via the API, re-verifies all checks green, and
merges through GitHub native auto-merge — then mints the release tag at the
merge-time CalVer.

This PR is the successor regression for the finalize-guard fix: its prose
legitimately names the finalize marker (`auto-merge-finalized`), the exact
phrase the old naive substring guard mistook for an already-finalized file —
which silently skipped the finalize and minted the release tag at the author's
placeholder stamp instead of the merge stamp. The fixed guard requires the
marker to carry the file's own basename stamp (the merge CalVer), a form prose
cannot contain, so a genuine placeholder is always finalized to the merge-time
CalVer and tagged with the merge stamp.

If the tag minted on this PR is `v2026.232.0004` (this placeholder) instead of
the merge-time CalVer, the guard defect has regressed. A correct engine run
must finalize this placeholder to the merge stamp before merging and tag the
merged HEAD with that stamp.
