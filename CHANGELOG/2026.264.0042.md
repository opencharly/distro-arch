# 2026.264.0042 — feat(distros): own the arch-family skills in distro-arch

## Summary

Move the seven arch-family `skill:` entities from the
`opencharly/layer-charly-distros` concept aggregator into this repo, the repo
that actually owns the artifacts they document:

- `arch`, `arch-builder`, `arch-aur-test`, `arch-pac-test`, `arch-test`
- `arch-coder`, `charly-arch` (owned by `distro-arch`'s `box/arch-coder` /
  `box/charly-arch` boxes)

Each entity is copied **verbatim** (same `name`/`family`/`description`/
`content`) and its `owner:` is corrected from the aggregator's
`charly-distros`/`charly-coder` to the skill's own name, matching the
ownership convention every single-candy repo already uses
(`layer-chrome` → `owner: chrome`, `pod-ollama` → `owner: ollama`).

The published corpus is UNCHANGED: `charly marketplace generate`'s emitter is a
pure function of a skill entity's `name`, `description`, `content`,
`references` and `type` (not its owning repo or `owner:`), so relocating a
source entity republishes byte-identical `SKILL.md` files. The marketplace's
refs-list pin addition and the aggregator-side deletion land as their own PRs;
the marketplace deploy drift gate proves the corpus stays byte-identical.

## How tested

`charly box validate` on this branch — the moved entities load, the repo's
schema accepts `skill:` nodes alongside its `defaults:`/`import:`/`discover:`
directives, and nothing else changed:

```
$ charly box validate
charly box validate: OK — checked 132 candies, 11 boxes, 8 deploys, 7 distros, 7 builders; 0 warnings, 0 errors
```

The emitter is a pure function of the entity fields (read from
`candy/plugin-marketplace`'s `emit_skills.go`): `emitSkillMarkdown` writes
`frontmatter(name, description) + generatedHeader + content` and nothing else.
Replicating it over the source entity text and comparing to the committed
corpus reproduced all 27 `distros`-family `SKILL.md` files byte-for-byte
(27/27), including the seven moved here. The marketplace PR's drift gate is the
end-to-end confirmation.

Pinning `distro-arch` into the generation closure was separately proven INERT:
adding `@github.com/opencharly/distro-arch:v2026.256.1135` to the refs list and
regenerating produced a **0-file diff** against the committed corpus (the repo
was already reachable transitively via `distro-cachyos`/`distro-omarchy`).
