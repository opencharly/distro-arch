# 2026.229.1420 — declare source.distro on the cloud_image VM

Placeholder CalVer (the pr-validator finalizes it at merge). Chosen after the newest entry
in this repo, with no filename or tag collision.

`source.distro` selects three things about a guest that nothing else in the spec implies: its
package NAME (`openssh` vs `openssh-server`), its package MANAGER (`pacman -Sy --needed` vs the
`packages:` cloud-config key) and its sshd UNIT name (`sshd` vs `ssh`).

It used to be INFERRED from `base_user`, and only for `arch` and `alpine` — every other distro
fell through to Arch/Fedora conventions. So a Debian-family image that omitted it was rendered
`openssh` + `systemctl enable --now sshd`, a unit Debian and Ubuntu do not have, and with
cloud-init's deliberate `mask ssh.socket` that left a socket-activated sshd masked and never
started: the guest booted fully and served nothing.

That inference is **being removed** in opencharly/spec#35 + opencharly/sdk#140, both of which are
still OPEN at the time of writing. Once they land, `spec.DistroSSHUnits[distro]` and
`spec.DistroInits[distro]` become bare lookups into tables generated from
`schema/distro_vocab.cue` with **no default**, and an absent distro will render an EMPTY sshd unit
name rather than silently meaning "Arch/Fedora conventions". Presence will be enforced at author
time by the vm kind's own OpValidate capability, which currently lives on an unmerged superproject
branch. Nothing of that is landed yet, so this repo's cloud_image source
must state `arch` explicitly.

## What is true TODAY, and why this is safe to land first

`spec@origin/main` types the field `distro?: string` — optional **and open** — and carries no
`schema/distro_vocab.cue` at all. So on today's main this change is **purely additive**: it cannot
trip closed-schema rejection and cannot break any current consumer. The closed `#DistroID`
vocabulary, the generated trait tables and the presence check all arrive later, with spec#35 /
sdk#140 / the superproject change.

That also settles the landing order: this repo can, and should, land FIRST. Once the sdk lookups
lose their default, a consumer repo that still omits `distro:` renders an empty unit name — so the
field wants to be in place before that, not after.

## Why this repo has to land before its consumers

Consumers pin this repo by tag. Their suites fail against the currently-pinned copy for exactly
this reason, so the tag minted on merge is what unblocks them.
